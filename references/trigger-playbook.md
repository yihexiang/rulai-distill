# reference · description 撰写与抢调用治理

> 蒸馏产物最常见的真实故障不是"不会做"，而是**两张卡互相抢调用**。本文只解决这一件事。

---

## 一、description 的最小结构

```yaml
description: |
  <动作用一句话讲清：在什么情境下，用什么方法，产出什么>（≤40 字）
  适用：<3-5 个具体情境，写用户会遇到的情形，不写能力名>
  不做：<2-3 个明确排除项，最好点名替代方案>
  English: <同上缩成英文一句，含 Use for / Do NOT use for>
```

**反面例子**（会导致抢调用）

```
description: 分析问题，提供结构化思路和可执行建议。
```

凡是"分析""结构化""可执行建议"这类词，几乎每个技能都能写，等于没写。

**正面例子**

```
description: |
  在多条线索互相冲突的排查场景里，按影响面排序决定先验证哪一条。
  适用：日志噪声大、多个异常同时出现、health check 全绿但功能异常。
  不做：已确认单一根因时的修复执行；单纯的信息检索与摘要。
```

---

## 二、四个字段的记忆点

| 字段 | 写什么 | 常见错误 |
|---|---|---|
| 动作句 | 情境 + 方法 + 产出 | 只写方法名，读者不知道何时用 |
| 适用 | 用户视角的**具体情形** | 写抽象能力词（"复杂的决策场景"） |
| 不做 | 排除 + 替代去向 | 省略；或写"不适用于其他场景"这类废话 |
| 语言信号 | **用户的口语原话** | 写成书面任务描述 |

> 语言信号必须是真实用户会说的话。「这两件事我到底先解决哪个」是对的；「请进行优先级排序」永远不会出现在真实对话里。

---

## 三、抢调用的三种根因与修法

| 根因 | 症状 | 修法 |
|---|---|---|
| A 与 B 功能描述重叠 | 两者都被触发或都不被触发 | 在两张卡的 description 里**互相点名**：「若 X 情况请用 <对方 slug>」 |
| A 是 B 的子集 | B 抢走 A 的调用 | 让 A 的 description 更窄更具体，把边界写死在首句 |
| 方法名相似但对象不同 | 混着触发 | 在 A2 段加「易混淆辨析」表，写清**对象差异**（如：本卡分析结构，对方分析人） |

**硬性要求**：同一个 package 内，任两张卡的 `contrasts-with` 必须**双向登记**。只改一张是无效的——触发决策发生时，另一张的描述里仍然没有这条分界信息。

## 四、全套验证清单（发之前跑）

```bash
# 1. 静态：卡边界有没有写、排除项有没有
python3 scripts/td.py validate <bundle>

# 2. 触发：用整包列表做选择题，不是判断题
#    → templates/TEST-SUITE.md.template，至少 1 条 pairwise
# 3. 交叉：A→B 和 B→A 各一条，单向通过不算数
# 4. 口语：所有 prompt 用真实用户措辞重写一遍
```

**通过线**：`should_trigger` 全中；`should_not_trigger` 全不中；pairwise 全对。任一不满足，先改 description 再发布。

## 五、跨技能优先级的排序规则

当有两张以上的卡同时成立时，按下面顺序裁决：

1. **有明确禁止项的优先**：B 明确写了"不做 X"，A 没写 → 选 A 的对手项
2. **更具体的优先**：窄卡 > 宽卡
3. **有前置依赖的靠后**：需要先跑别的卡才能用的，让前置先裁决
4. **用户点名的优先**：用户明确说了方法名/卡片名，直接走，不做二次判断

> 第 4 条会覆盖前三条，但要在回答里说明"你指定了 X；不过按这个方法原本更适合用 Y，要不要换？"
