# 阶段 1.6 · 晋级门

> 问：这个能力值不值得成为**独立可触发的技能**，还是只做卡片挂在路由入口下？

## 为什么要设这道门

一本书拆出 20 个独立技能，部署后的头号故障是**互相抢调用**：用户问"我该先做什么"，20 个技能都声称能回答，Agent 随机挑一个。

晋级门是控制技能数量的**唯一机制**。宁可少几个独立技能，也不要制造抢调用的技能包。

## 五项判据

| 判据 | 问题 | 通过标准 |
|---|---|---|
| `independent_intent` | 有独立的用户意图吗？ | 存在一组用户 query 只对应这个能力 |
| `independent_contract` | 输入输出边界清楚吗？ | 能一句话说清"什么输入、产出什么" |
| `independent_run` | 能独立执行吗？ | 不需要先跑别的能力才成立 |
| `independent_reuse` | 会反复用到吗？ | 至少 3 个不同场景会触发 |
| `independent_eval` | 能机械判分吗？ | 能构造出有明确对错的测试用例 |

## 判定矩阵

| 组合 | 去向 | 说明 |
|---|---|---|
| 5/5 | **promoted** 独立 Skill | 完整安装，有自己的 SKILL.md |
| 4/5 | **router**（优先） | 挂路由表，不单独发布 |
| 3/5 | router | 合并进相邻能力的卡片 |
| ≤2/5 | 背景素材 | 写进 I 段或 glossary，不做成能力 |

**注意非全有全无**：`independent_reuse` 最容易失败——只在一个特定场景有用、换个场景就不成立的能力，做成独立技能只会稀释触发精度。

## 预算约束

`promotion_budget`（默认 8）是硬约束，不是建议。

理由：每多一个独立技能，Agent 每次任务都要在 N 个 description 之间做选择。**触发精度随技能数量单调下降**。

一本书 190 万字产出 18 个技能已是偏多；超过 20 个时，应主动合并相关能力，或把 `independent_reuse` 不足的降级为 router。

## 晋级后必做

晋级为独立技能，**必须同时完成**：

1. 写清与相邻技能的**易混淆辨析**（对比表或三问：什么时候用 A 而不是 B）
2. 准备诱饵测试用例，且**至少 1 条诱饵指向某个真实存在的兄弟技能**
3. 在 frontmatter 明确写出**不适用场景**

跳过这三条，晋级只会增加噪音。

## 反模式

❌ "这个内容很丰富，拆成 3 个技能吧"
→ 丰富不等于可触发。检查 `independent_reuse`。

❌ "A 是 B 的一部分，但 A 也很重要"
→ 重要不等于独立。检查 `independent_run`。

❌ "先做出来再说，触发问题以后调"
→ 触发精度不能靠后期调。触发描述是从 A2 段的"语言信号"直接提取的，A2 没写清楚，后期也补不上。
